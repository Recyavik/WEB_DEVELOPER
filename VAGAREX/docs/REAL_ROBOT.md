# VEGAREX на реальном 1Т REX — полное руководство

Этот документ описывает запуск VEGAREX на физическом 1Т REX: три режима
подключения, голосовое управление, выгрузку экспортированных программ,
калибровку, заглушку `_Bridge` для теста без железа, и поиск
неполадок.

Зеркало раздела справки `/hardware` в проекте — то же содержимое для
оффлайнового чтения.

## Архитектура

### Три режима работы

VEGAREX работает с роботом через единый интерфейс `self.robot` (см.
`robot_driver.py`), за которым стоит один из трёх драйверов. Выбор — в
Настройках («Соединение с роботом»).

| Режим | Когда использовать | Что требуется |
|---|---|---|
| **Симулятор** (галочка «Включить симулятор») | Разработка, тренировка, миссии без железа | Ничего — всё в браузере |
| **Мост `server.py`** (host: `ws://...`) | Боевой режим: голос + физический 1Т REX | Запущенный `server.py`, подключённый ESP32 (WiFi или USB) |
| **Прямой TCP** (host: `IP:port`) | Старая плата REX Board без `server.py` | Робот в той же WiFi-сети, открытый TCP-порт |

### Путь сигнала (с мостом)

```
голос (Web Speech API) → браузер → VEGAREX FastAPI server
                                        ↓ NLU
                                        ↓ _run_forward / _run_arc / face / goto / ...
                                        ↓ self.robot ← BridgeDriver
                                        ↓
                              ws://127.0.0.1:41235
                                        ↓
                                   server.py
                                        ↓ (WiFi или USB-Serial)
                                ESP32 / 1Т REX
```

Голос распознаётся в браузере, отправляется в VEGAREX server, NLU
(`nlu.py`) парсит, `session.py` исполняет шаблон манёвра (face / goto /
forward / arc / ...), который через `BridgeDriver` шлёт примитивные
команды (`MOVE:40`, `ANGLE:36`) на `server.py`. `server.py` —
прозрачный мост, который пересылает их на ESP32 по WiFi-WebSocket или
USB-Serial.

> **Важно:** никаких шаблонов на робот не уходит. Вся высокоуровневая
> логика (K-turn, A*-планировщик, проверка зон, дуги по калибровке)
> исполняется на сервере VEGAREX. На железо идут только
> `MOVE/ANGLE/LASER?/RGB` — те же команды, что у `RexDriver` в прямом
> TCP-режиме.

## Подключение

### Через `server.py` (рекомендуется)

#### Что такое `server.py`

Отдельная программа на Python с GUI (tkinter), которая работает
«прозрачным мостом» между браузером и ESP32. Имеет два WebSocket-сервера:
один для клиентов (порт **41235**), второй для самого робота (порт
**8080**). Также умеет общаться с ESP32 через USB-Serial (если робот
подключён кабелем).

#### Шаги подключения

1. Запусти `server.py` на компьютере (двойной клик или `python server.py`).
   Откроется окно «Car Server».
2. В GUI выбери **IP-адрес ПК** (тот, к которому подключится ESP32) и
   нажми **«Соединить»**.
3. Подключи робота:
   - **WiFi:** ESP32 загружен с прошивкой, знает SSID твоей сети и
     IP-адрес ПК. Подключится сам, как только `server.py` запущен.
     Признак — индикатор «Машинка» в GUI стал зелёным.
   - **USB:** кабель в USB-порт ПК. В GUI `server.py` выбери COM-порт и
     при отправке команд ставь `usb=true` (VEGAREX делает это
     автоматически, если host начинается с `ws://`).
4. В VEGAREX → Настройки → **Соединение с роботом**:
   - Сними галочку **«Включить симулятор»**.
   - В поле **«Адрес»** впиши `ws://127.0.0.1:41235` (если `server.py` на
     этом же ПК) или адрес другого ПК с `server.py`.
   - Поле **«Порт»** для WS-режима игнорируется (порт уже в URL), но
     должно быть валидным значением.
   - Жми **«Сохранить»** — соединение переустановится.
5. Готово. Все команды (кнопки, голос, Python-код) идут через мост на
   реальный робот.

> Робот сам разместить препятствия не сможет — координаты опасных зон
> нужно загрузить программой через `robot.load_danger_zones([(x,y,r), …])`
> в начале программы.

### Прямой TCP к REX Board

Старый режим — без `server.py`, напрямую к плате REX Board по WiFi. В
Настройках:

- Сними «Включить симулятор».
- Адрес: `192.168.1.100` (IP робота в твоей сети) — БЕЗ `ws://`.
- Порт: `8765` по умолчанию.

Команды идут как plain TCP, тот же словарь (`MOVE:N\n`, `ANGLE:N\n`, …).
Используется, если у тебя плата REX Board без прошивки моста ESP32.

### Симулятор (без железа)

Поставь галочку «Включить симулятор». Никакого `server.py` или робота не
нужно. Виртуальная физика, голосовые команды, миссии — всё в браузере.
Идеально для разработки алгоритмов до выезда на поле.

## Использование

### Голосовые команды на железе

Работают точно так же, как в симуляторе. **Менять ничего не нужно.**
Браузер распознаёт фразу через Web Speech API, шлёт текст в VEGAREX, NLU
парсит, шаблон манёвра исполняется, через `BridgeDriver` команды идут на
робота.

| Фраза | Что делает |
|---|---|
| `Вега вперёд 50 см` | Едет вперёд на 50 см |
| `Вега назад 30 см` | Едет назад на 30 см |
| `Вега лицом к 90` | K-turn до курса 90° (восток) |
| `Вега в точку 100 50` | Доехать в точку (100, 50) |
| `Вега автопилот 200 150` | A*-планировщик до (200, 150) |
| `Вега стоп` | Мгновенная остановка |
| `Вега медленно / спокойно / быстро` | Скорость 30 / 40 / 80 % |

**Подсказка по микрофону:** Web Speech API в Chrome/Edge требует HTTPS
для удалённого хостинга, но на `localhost` работает без него. Если
VEGAREX крутится на твоём ПК и слушаешь его в браузере на том же ПК —
голос работает без сертификатов.

### Запуск экспортированного `.py`

Кнопка `</>` в редакторе собирает self-contained Python с шаблонами
манёвров и классом `Robot`. Этот файл можно запустить ОТДЕЛЬНО от
VEGAREX — он сам общается с роботом через `server.py`.

1. В редакторе нажми **`</>`** — откроется модалка «Сборка кода для робота».
   Внутри готовый Python.
2. Нажми **«⬇ Скачать .py»** — файл сохранится с именем
   `vegarex_program_YYYY-MM-DD.py`.
3. В скачанном файле найди внизу две строки:
   ```python
   robot = _LiveRobot()              # тест на ПК без железа
   # robot = _NetworkRobot()         # боевой режим через server.py
   ```
   Закомментируй первую, раскомментируй вторую.
4. Установи зависимость:
   ```
   pip install websocket-client
   ```
5. Запусти `server.py`, подключи робота (см. §Подключение).
6. Запусти программу:
   ```
   python vegarex_program_YYYY-MM-DD.py
   ```

Программа подключится к `ws://127.0.0.1:41235` (адрес меняется в коде,
константа `_NetworkBridge.BROWSER_WS_HOST`), пошлёт команды на ESP32 и
выполнит алгоритм. В консоли увидишь предупреждения о зонах и итоговые
сообщения.

### Опасные зоны на поле

В симуляторе зоны — это объекты в браузере. На реальном поле — это
физические препятствия (коробки, стаканы, конусы), которые ты ставишь в
известные координаты. Робот сам не «видит» их (только дальномером
спереди), но при дед-рекoning'е знает свои координаты и проверяет
позицию против списка зон.

#### Как загрузить список зон

```python
DANGER_ZONES = [
    (-151.0, -48.0, 25.0),   # (x, y, радиус) в см
    (51.0,    61.0, 10.0),
]
robot.load_danger_zones(DANGER_ZONES)
```

#### Что произойдёт во время движения

Внутри `forward / back / arc / face / spiral` каждые 50 мс проверяется
текущая позиция против списка опасных зон с запасом `ROBOT_SAFETY_CM`.
При въезде в зону — стоп с сообщением `⛔ Опасная зона (x, y) r=… —
стоп.`

#### Удалить зону программно

```python
robot.remove_zone_here()          # снять зону, в которой стоит робот
robot.remove_zone(51, 61)         # снять конкретную
```

Используется когда обучающийся ФИЗИЧЕСКИ убрал препятствие — после этого
программа сможет проехать через эти координаты.

## Заглушка `_Bridge`

### Что это и зачем

Когда жмёшь `</>` в редакторе, в собранном файле есть два класса-моста:
`_Bridge` (заглушка) и `_NetworkBridge` (реальный мост через
`server.py`). По умолчанию активна заглушка — `robot = _LiveRobot()`.

`_Bridge` — это **синтаксический скелет** низкоуровневого API. Не
имитация, не симулятор — именно скелет: все методы `pass`, свойства
`x/y/heading` зафиксированы на 0.

Цель — позволить экспортированному `.py` запуститься на ПК БЕЗ
чего-либо: без `websocket-client`, без запущенного `server.py`, без
подключённого ESP32. Файл должен импортироваться и пройти до конца, не
сломавшись.

```python
class _Bridge:
    """Заглушка для теста кода на ПК БЕЗ робота."""
    x = 0.0
    y = 0.0
    heading = 0.0

    def set_angle(self, deg): pass
    def move(self, pct):      pass
    def stop(self):           pass
    def set_rgb(self, idx, color, delay=0.0): pass
    def get_distance(self):   return 999.0
```

### Как вплетается в архитектуру

Высокоуровневый класс `Robot` (forward, arc, face, goto, …) внутри своих
методов делает `self.set_angle(...)`, `self.move(...)` и т.д. — то есть
зовёт низкоуровневое API. Python через MRO находит эти методы у
`_Bridge` (родителя в `_LiveRobot(_Bridge, Robot)`). Поскольку методы
`_Bridge` — `pass`, ничего физически не происходит. А Python-логика
выше (циклы, условия, проверки зон, формулы) — работает нормально.

### Что работает с заглушкой ✓

- Импорт файла, синтаксис — никаких внешних зависимостей
- Запуск программы до конца (`python file.py`)
- `robot.load_danger_zones(...)`, `show_danger_zones()`,
  `remove_zone()`, `attention_here()` — это просто запись/чтение списков
- Диагностические `print()` — зональные предупреждения,
  `WARN: скорость …`
- Контекстная инициализация — расчёт `target_heading`, `dist`,
  `cm_per_s`
- Метрики времени — `time.sleep()` внутри `_drive_with_zone_check`
  действительно тикает

### Что НЕ работает с заглушкой ✗

- **Движение робота** — мотор/серва не дёргаются
- **x, y, heading** не обновляются — всегда 0.0
- **`get_distance()`** возвращает 999.0 (см. ниже)
- **`forward_to_wall()`** — зависнет навечно: ждёт
  `get_distance() < WALL_STOP_CM`, но 999 > 12
- **`face(target)`** — отработает 3 пары forward+back (тик-сны), но
  `heading` останется 0. Если потом `goto()` считал, что повернулся —
  он ошибётся.
- **`goto(50, 60)`** — сделает все вычисления, проспит положенное время,
  но `x/y` не сдвинутся. После 3 попыток «не дошёл» — выходит.
- **Сенсорные ветки** (`if robot.get_distance() < 50`) — всегда False
  (999 > 50)

### Почему `get_distance()` возвращает 999.0

`Robot.forward_to_wall()` опрашивает дальномер в цикле, пока расстояние
> `WALL_STOP_CM`. Заглушка должна вернуть *что-то*. 999 = «бесконечно
далеко» — не вызывает мгновенного срабатывания «упёрся в стену». На
реальном железе `_NetworkBridge.get_distance()` шлёт `LASER?` и парсит
ответ.

### Почему методы — `pass`, а не `print`

В версии v3.4.0 здесь были `print("[bridge] set_angle(36)")` и т.п. Идея
— видеть в консоли поток команд при dry-run. Но `_Bridge` целиком
заменяется на `_NetworkBridge` на железе — print'ы там не появлялись, а
на ПК они *шумели* при каждом тике. Дешевле сделать заглушку тихой.

Если хочешь видеть поток команд при dry-run — добавь в свою копию
шаблона `print()` обратно, или ещё лучше — добавь `_DEBUG = True` флаг.

### Когда использовать и как переключаться

| Сценарий | Бридж |
|---|---|
| Проверить, что код парсится и API всё на месте | `_LiveRobot()` |
| Прогнать программу на ПК, посмотреть журнал | `_LiveRobot()` |
| Поправить шаблоны в `Robot` и проверить локально | `_LiveRobot()` |
| Запустить реальный 1Т REX через server.py | `_NetworkRobot()` |
| Написать свой мост (BLE, ESP-Now, прямой TCP) | Унаследовать от `Robot`, заменить `_Bridge` |

Внизу файла:

```python
robot = _LiveRobot()              # ← по умолчанию (заглушка)
# robot = _NetworkRobot()         # ← раскомментируй для железа
```

Меняешь местами комментарии — и тот же код работает или в заглушке, или
на роботе. Программа выше не изменится.

## Калибровка

Симулятор и реальный 1Т REX едут синхронно только если калибровочные
константы соответствуют физическим характеристикам твоей машинки.
Настраиваются в `config.py` или прямо в Настройках UI.

| Параметр | Дефолт | Что это |
|---|---|---|
| `SPEED_AT_100` | 80.0 см/с | Линейная скорость при 100% мощности мотора. Замерь: запусти `robot.forward(100, speed=100)`, засеки секундомером. |
| `WHEEL_CIRC_CM` | 28.3 см | Длина окружности колеса. Для D90: π × 9 ≈ 28.3 см. |
| `HEADING_DEG_PER_ROT` | 25.0° | Сколько градусов курса набегает за один оборот колеса при полном угле руля (45°). Зависит от колёсной базы и радиуса поворота. Замерь: поставь руль на 45°, проедь известную длину дуги, замерь смену курса по компасу. |
| `TURN_SPEED_REF` | 40 % | Опорная скорость, на которой откалиброван `HEADING_DEG_PER_ROT`. Все геометрические манёвры (arc, K-turn, set_course, …) всегда едут на этой скорости — чтобы дуги были одинаковыми в симе и на железе. |
| `MOVE_SPEED` | 40 % | Скорость по умолчанию для прямых `forward/back`. Можно менять кнопками в UI (MIN/Спокойно/Быстро/MAX). |
| `MIN_SPEED_PCT` | 30 % | Минимум — ниже мотор не тянет (рывки, остановки). Все попытки установить меньше клэмпаются автоматически. |

> **На v3.4.4 значения дефолтные.** Если на реальном поле траектории не
> сходятся с симулятором (робот промахивается по точкам, дуги шире/уже)
> — нужно подкалибровать.

## Поиск и устранение неполадок

| Проблема | Что проверить |
|---|---|
| Робот не двигается, в журнале «Bridge connect failed» | 1) `server.py` запущен и «Соединить» нажато? 2) В Настройках адрес `ws://127.0.0.1:41235`? 3) Индикатор «Браузер» в GUI `server.py` зелёный? Перезапусти соединение в Настройках (Сохранить). |
| «Машинка» в GUI `server.py` красная | ESP32 не подключился. WiFi-режим: ESP32 знает SSID и пароль сети (проверь через GUI `server.py` → «Получить»); IP-адрес ПК в настройках ESP32 совпадает с выбранным в GUI. USB-режим: правильный COM-порт; ESP32 виден в системе. |
| Робот двигается, но дальномер всегда показывает 999 | Прошивка ESP32 не отвечает на `LASER?`. Проверь в `server.py` в режиме «Отладка Serial»: пошли вручную `LASER?`. Должен прийти ответ типа «LASER:42.5» или «42.5». |
| Дуги в симуляторе и на роботе разной формы | Калибровка. См. §Калибровка. Самое частое — неверный `HEADING_DEG_PER_ROT` или `WHEEL_CIRC_CM`. |
| Робот промахивается по точкам в `goto` | Накапливается дрейф dead-reckoning. Причины: проскальзывание шин, неверная `SPEED_AT_100`, батарея просела (мотор недодаёт). Калибровка + MPU-гироскоп для курса. |
| Голос «Вега вперёд 50» не распознаётся | Web Speech API работает только в Chrome/Edge. Микрофон должен быть разрешён (значок в адресной строке). На удалённом хостинге нужен HTTPS, на `localhost` — без сертификатов. |
| Робот въезжает в препятствие, программа не реагирует | 1) Зоны загружены в `robot.load_danger_zones(...)`? 2) Координаты препятствий совпадают с реальными? 3) В Настройках «Препятствия → ⛔ Опасные зоны» включено? Робот не «видит» препятствия в физическом мире — только через свой dead-reckoning + загруженный список зон. |
| Экспортированный `.py` падает: `ModuleNotFoundError: websocket` | `pip install websocket-client` на той машине, где запускаешь скачанный файл. **Важно:** именно `websocket-client`, не `websocket`. |

## Глоссарий

**1Т REX** — физический образовательный робот (4-колёсный, с
рулевым управлением, дальномером, RGB-LED). Контроллер на базе ESP32
или REX Board.

**ESP32** — микроконтроллер на роботе. На него прошивается код, который
понимает командный словарь VEGAREX (`MOVE`, `ANGLE`, `LASER?` и т.д.).

**REX Board** — старая плата 1Т REX без ESP32. Подключается по TCP
напрямую — без `server.py`.

**`server.py`** — программа-мост на Python с GUI (поставляется
отдельно). Соединяет браузер (WS 41235) и робота (WS 8080 или
USB-Serial). Транзитом пересылает команды в обе стороны.

**BridgeDriver** — класс в `robot_driver.py`. Async WebSocket-клиент к
`server.py`. Реализует тот же интерфейс, что `RexDriver` и `SimDriver`,
но шлёт команды через мост.

**RexDriver** — прямой TCP-драйвер к REX Board (старый режим).

**SimDriver** — виртуальный драйвер для режима «Симулятор».

**`_Bridge`** — заглушка в экспортированном `.py`. Все методы `pass`.
Для теста кода на ПК БЕЗ железа.

**`_NetworkBridge`** — реальный мост в экспортированном `.py`.
Async WebSocket-клиент к `server.py`, по сути та же логика, что
BridgeDriver, но синхронная (через `websocket-client` пакет).

**Dead-reckoning** — счисление пути по времени × скорости × углу руля,
без обратной связи от датчиков. Точность ограничена калибровкой и
проскальзыванием шин. Используется и в симуляторе (`update_physics`),
и в `_NetworkBridge` (фоновый поток).

**Web Speech API** — браузерный API распознавания речи. Доступен в
Chrome / Edge. Принимает аудио с микрофона, возвращает текст.

**NLU** — Natural Language Understanding. Модуль `nlu.py` парсит
русские фразы вида «Вега вперёд 50 см» в структуру `RobotCmd` с
интентом и параметрами.
