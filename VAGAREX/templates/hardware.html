🔌 Реальный 1Т REX

Документация по запуску VEGAREX на физическом 1Т REX. Включает три режима подключения, голосовое управление на железе, выгрузку экспортированного .py, калибровку, заглушку _Bridge и поиск типичных проблем.

1. Архитектура

1.1. Три режима работы

VEGAREX работает с роботом через единый интерфейс self.robot (см. Справка → API 1T REX), за которым стоит один из трёх драйверов. Выбор — в Настройках («Соединение с роботом»).

РежимКогда использоватьЧто требуется
Симулятор (галочка «Включить симулятор») Разработка, тренировка, миссии без железа Ничего — всё в браузере
Мост bridge.py (host: ws://...) Боевой режим: голос + физический 1Т REX Запущенный bridge.py, подключённый ESP32 (WiFi или USB)
Прямой TCP (host: IP:port) Старая плата REX Board без bridge.py Робот в той же WiFi-сети, открытый TCP-порт

1.2. Путь сигнала (с мостом)

голос (Web Speech API) → браузер → VEGAREX FastAPI server ↓ NLU ↓ _run_forward / _run_arc / face / goto / ... ↓ self.robot ← BridgeDriver ↓ ws://127.0.0.1:41235 ↓ bridge.py ↓ (WiFi или USB-Serial) ESP32 / 1Т REX

Голос распознаётся в браузере, отправляется в VEGAREX server, NLU (nlu.py) парсит, session.py исполняет шаблон манёвра (face / goto / forward / arc / ...), который через BridgeDriver шлёт примитивные команды (MOVE:40, ANGLE:36) на bridge.py. bridge.py — прозрачный мост, который пересылает их на ESP32 по WiFi-WebSocket или USB-Serial.

Никаких шаблонов на робот не уходит. Вся высокоуровневая логика (K-turn, A*-планировщик, проверка зон, дуги по калибровке) исполняется на сервере VEGAREX. На железо идут только MOVE/ANGLE/LASER?/RGB — те же команды, что у RexDriver в прямом TCP-режиме.

2. Подключение

2.1. Через bridge.py (рекомендуется)

Что такое bridge.py

Лёгкий headless-скрипт (~140 строк, без GUI), который работает «прозрачным мостом» между VEGAREX и ESP32. Лежит в репозитории в папке VAGAREX/bridge.py. Открывает два WebSocket-сервера: :41235 для VEGAREX/браузера и :8080 для ESP32 по WiFi. По флагу --com дополнительно подключается к ESP32 по USB-Serial.

Установка зависимостей (один раз)

В PowerShell или терминале на хосте (вашем ПК):

pip install websockets pyserial-asyncio

websockets — обязательно (релей); pyserial-asyncio — только для USB-режима, можно поставить позже.

Запуск моста

Три варианта (зависит от того, как запущен VEGAREX):

  1. VEGAREX в Docker (docker-compose): bridge теперь сервис в docker-compose.yml и стартует автоматически вместе с app и db: 
    docker compose up -d --build
    Никаких ручных команд. В Настройках адрес — ws://bridge:41235 (Docker DNS). Порт 8080 проброшен на хост для подключения ESP32 по WiFi.
  2. VEGAREX нативно (без Docker): Используй кнопку 🚀 Запустить bridge.py в Настройках — она запустит фоновый процесс на твоём ПК. Или вручную: 
    cd VAGAREX
python bridge.py                # только WiFi
python bridge.py --com COM3     # WiFi + USB-Serial
    Адрес в Настройках — ws://127.0.0.1:41235.
  3. USB-Serial на хосте (любой режим): Docker не пробрасывает COM-порты, поэтому для USB всегда запускай python bridge.py --com COMx на хосте — он перехватит порт 41235 раньше, чем bridge из контейнера (или просто отключи bridge-сервис: docker compose stop bridge).

В логах увидите:

  • [BROWSER] подключён — VEGAREX установил соединение
  • [ESP32] подключён — робот вышел на связь по WiFi
  • [→WiFi] MOVE:40 / [→USB] ... — поток команд от VEGAREX
  • [WiFi→] / [USB→] — ответы робота

Настройки VEGAREX

В Настройки → Соединение с роботом:

  • Снимите галочку «Включить симулятор»
  • В поле «Адрес» впишите один из:
    • ws://bridge:41235 — VEGAREX и мост в одном docker-compose (рекомендуется)
    • ws://host.docker.internal:41235 — VEGAREX в Docker, мост на хосте
    • ws://127.0.0.1:41235 — VEGAREX и bridge.py на одном ПК (без Docker)
    • ws://192.168.x.y:41235 — мост на другом ПК в той же сети
    • wss://<name>.trycloudflare.com — VEGAREX в продакшне, мост дома через туннель (см. §2.5)
  • Поле «Порт» для WS-режима не используется (порт уже в URL)
  • Нажмите «Сохранить» — соединение переустановится

Робот сам разместить препятствия не сможет — координаты опасных зон нужно загрузить программой через robot.load_danger_zones([(x,y,r), …]) в начале программы. См. §3.3.

2.2. Прямой TCP к REX Board

Старый режим — без bridge.py, напрямую к плате REX Board по WiFi. В Настройках:

  • Снимите «Включить симулятор».
  • Адрес: 192.168.1.100 (IP робота в вашей сети) — БЕЗ ws://.
  • Порт: 8765 по умолчанию.

Команды идут как plain TCP, тот же словарь (MOVE:N\n, ANGLE:N\n, …). Используется, если у вас плата REX Board без прошивки моста ESP32.

2.3. Симулятор (без железа)

Поставьте галочку «Включить симулятор». Никакого bridge.py или робота не нужно. Виртуальная физика, голосовые команды, миссии — всё в браузере. Идеально для разработки алгоритмов до выезда на поле.

2.4. Первый запуск нового ESP32 (один раз)

Когда у вас новый робот (или сменили WiFi-сеть) — нужно прошить в EEPROM ESP32 имя сети, пароль и IP сервера с bridge.py. Эти настройки запоминаются на плате, после чего робот сам подключится к WiFi и к мосту при каждом включении.

Через браузер (рекомендуется)

  1. Подключите ESP32 по USB-кабелю к вашему ПК.
  2. Откройте VEGAREX → Настройки → кнопка 🛠 Настроить ESP32 (или прямо /esp-config).
  3. Жмите 🔌 Подключиться к ESP32 — браузер попросит выбрать COM-порт. Выбирайте тот, где ESP32 (обычно с описанием USB-SERIAL CH340, Silicon Labs CP210x или USB Serial Port).
  4. Заполните поля:
    • Имя WiFi (SSID) — имя вашей сети (или точки доступа телефона)
    • Пароль WiFi
    • Имя устройства — произвольное (например rex01)
    • IP сервера — IP вашего ПК в этой WiFi-сети (по которому виден из сети)
    • Порт сервера — 8080 по умолчанию
  5. Жмите 📤 Записать в EEPROM. В логе должны появиться ← OK или подобные подтверждения.
  6. Отключите USB — настройки сохранены навсегда (до следующей перепрошивки).

Браузерная страница использует Web Serial API (только Chrome и Edge на десктопе). USB-доступ — у браузера, не у Docker-контейнера VEGAREX, поэтому работает в любом окружении.

Запасной путь — esp_config.py (Firefox/Safari)

Если ваш браузер не поддерживает Web Serial — используйте нативную утилиту из репозитория: 

cd m:\WEB_DEVELOPER\VAGAREX
pip install pyserial
python esp_config.py

Откроется маленькое tkinter-окно с теми же полями. Логика идентичная браузерной версии.

2.5. Продакшн (vegarex.dev.appswire.ru) через cloudflared-туннель

Сценарий: VEGAREX крутится на удалённом сервере (Coolify, домен vegarex.dev.appswire.ru), а робот стоит дома — в WiFi рядом с твоим ноутбуком. Чтобы серверный BridgeDriver в облаке дотянулся до локального bridge.py через NAT — поднимаем cloudflared-туннель.

Архитектура

браузер ──https──→ VEGAREX (vegarex.dev.appswire.ru, Coolify) ↓ BridgeDriver wss://<имя>.trycloudflare.com ↓ (cloudflared edge) cloudflared на ноуте (исходящий) ↓ ws://localhost:41235 ↓ bridge.py на ноуте ↓ (WiFi LAN) ESP32 / 1Т REX

Туннель идёт изнутри-наружу, поэтому домашний NAT/файрвол открывать не нужно. ESP32 продолжает стучать в локальный IP ноута:8080 как и в локальном сценарии — про облако робот не знает.

Шаг 1. Установить cloudflared на ноутбук (один раз)

Скачать cloudflared с сайта Cloudflare (Windows: .msi или .exe). После установки: 

cloudflared --version

Шаг 2. Запустить локально bridge.py

Либо через docker-compose в репозитории VEGAREX: 

cd m:\WEB_DEVELOPER\VAGAREX
docker compose up -d bridge

Либо без Docker:

python bridge.py

В обоих вариантах bridge слушает ws://localhost:41235.

Шаг 3. Поднять туннель

В отдельном окне терминала:

cloudflared tunnel --url http://localhost:41235

В первые секунды в выводе появится строка вида: 

+--------------------------------------------------------------+
|  https://random-name-1234.trycloudflare.com                  |
+--------------------------------------------------------------+

Это публичный URL твоего bridge. Скопируй его. Окно cloudflared должно оставаться открытым всё время работы с роботом.

Free-режим (--url) даёт случайный URL, который сменится после перезапуска cloudflared. Для стабильного URL — именованный туннель через Cloudflare-аккаунт (бесплатно, но нужен свой домен).

Шаг 4. Прописать URL туннеля в VEGAREX

Откройте https://vegarex.dev.appswire.ru/settings. В блоке «Соединение с роботом»:

  • Снимите «Включить симулятор».
  • В поле «Адрес» вставьте URL туннеля, заменив https:// на wss://: wss://random-name-1234.trycloudflare.com
  • Нажмите «Сохранить».

VEGAREX-сервер откроет WSS-соединение к Cloudflare edge → туннель → ws://localhost:41235 → ваш bridge.

Шаг 5. ESP32 — без изменений

В /esp-config по-прежнему пишем локальный IP вашего ПК в той WiFi-сети (например 192.168.x.y) и порт 8080. ESP32 ходит к bridge на ноуте по LAN, не через интернет. Это и есть выгода Сценария 2: минимальный пинг до робота, командный канал в облако — отдельная история.

Проверка цепочки

  1. В логах bridge.py: [BROWSER] подключён: (172.x.x.x, …) — это сервер VEGAREX из облака пришёл через туннель.
  2. Включите ESP32 → через ~5 сек в тех же логах: [ESP32] подключён: (192.168.x.y, …).
  3. В шапке VEGAREX в браузере индикатор → ● Онлайн.
  4. Команда RGB / forward — поток в трёх местах: браузер DevTools, лог bridge, светодиоды/мотор робота.

Подводные камни

  • Free-URL живёт пока открыто окно cloudflared. Закрыл окно → URL умер → нужно поставить новый в Настройки.
  • Cold-start задержка ~30-100 мс на каждой команде: браузер → Coolify → Cloudflare edge → твой ноут. Для команд робота нормально, для real-time телеметрии (LASER? на каждый тик) — возможны рывки.
  • Cloudflare режет неактивные WSS через 100 секунд idle. BridgeDriver должен переподключаться сам — следи за индикатором.
  • Ноут должен бодрствовать. Уход в сон = разрыв. Полезно в настройках Windows отключить «Сон» на время сессии.
  • Не публикуй URL туннеля. Любой, кто его знает, может слать команды моторам. Free-URL длинный и рандомный (как невзламываемый токен), но не должен попадать в публичные репо/чаты.

Альтернатива — ngrok

Если cloudflared не идёт — ngrok tcp 41235 работает аналогично. Минусы free-плана ngrok: рекламная страница для HTTP, для TCP — отдельный регион, URL вида tcp://0.tcp.eu.ngrok.io:NNNNN (в Настройках вписываем как ws://0.tcp.eu.ngrok.io:NNNNN).

3. Использование

3.1. Голосовые команды на железе

Работают точно так же, как в симуляторе. Менять ничего не нужно. Браузер распознаёт фразу через Web Speech API, шлёт текст в VEGAREX, NLU парсит, шаблон манёвра исполняется, через BridgeDriver команды идут на робота.

ФразаЧто делает
Вега вперёд 50 смЕдет вперёд на 50 см
Вега назад 30 смЕдет назад на 30 см
Вега лицом к 90K-turn до курса 90° (восток)
Вега в точку 100 50Доехать в точку (100, 50)
Вега автопилот 200 150A*-планировщик до (200, 150)
Вега стопМгновенная остановка
Вега медленно / спокойно / быстроСкорость 30 / 40 / 80 %

Подсказка по микрофону: Web Speech API в Chrome/Edge требует HTTPS для удалённого хостинга, но на localhost работает без него. Если VEGAREX крутится на вашем ПК и вы слушаете его в браузере на том же ПК — голос работает без сертификатов.

3.2. Запуск экспортированного .py

Кнопка </> в редакторе собирает self-contained Python с шаблонами манёвров и классом Robot. Этот файл можно запустить ОТДЕЛЬНО от VEGAREX — он сам общается с роботом через bridge.py.

  1. В редакторе нажмите </> — откроется модалка «Сборка кода для робота». Внутри готовый Python.
  2. Нажмите «⬇ Скачать .py» — файл сохранится с именем vegarex_program_YYYY-MM-DD.py.
  3. В скачанном файле найдите внизу две строки: 
    robot = _LiveRobot()              # тест на ПК без железа
# robot = _NetworkRobot()         # боевой режим через bridge.py
    Закомментируйте первую, раскомментируйте вторую.
  4. Установите зависимость: 
    pip install websocket-client
  5. Запустите bridge.py (или поднимите Docker-сервис bridge), подключите робота (см. §2.1).
  6. Запустите программу: 
    python vegarex_program_YYYY-MM-DD.py

Программа подключится к ws://127.0.0.1:41235 (адрес меняется в коде, константа _NetworkBridge.BROWSER_WS_HOST), пошлёт команды на ESP32 и выполнит алгоритм. В консоли увидите предупреждения о зонах и итоговые сообщения.

3.3. Опасные зоны на поле

В симуляторе зоны — это объекты в браузере. На реальном поле — это физические препятствия (коробки, стаканы, конусы), которые вы ставите в известные координаты. Робот сам не «видит» их (только дальномером спереди), но при дед-рекoning'е знает свои координаты и проверяет позицию против списка зон.

Как загрузить список зон

DANGER_ZONES = [
    (-151.0, -48.0, 25.0),   # (x, y, радиус) в см
    (51.0,    61.0, 10.0),
]
robot.load_danger_zones(DANGER_ZONES)

Что произойдёт во время движения

Внутри forward / back / arc / face / spiral каждые 50 мс проверяется текущая позиция против списка опасных зон с запасом ROBOT_SAFETY_CM. При въезде в зону — стоп с сообщением ⛔ Опасная зона (x, y) r=… — стоп.

Удалить зону программно

robot.remove_zone_here()          # снять зону, в которой стоит робот
robot.remove_zone(51, 61)         # снять конкретную

Используется когда обучающийся физически убрал препятствие — после этого программа сможет проехать через эти координаты.

4. Заглушка _Bridge

4.1. Что это и зачем

Когда жмёшь </> в редакторе, в собранном файле есть два класса-моста: _Bridge (заглушка) и _NetworkBridge (реальный мост через server.py). По умолчанию активна заглушка — robot = _LiveRobot().

_Bridge — это синтаксический скелет низкоуровневого API. Не имитация, не симулятор — именно скелет: все методы pass, свойства x/y/heading зафиксированы на 0.

Цель — позволить экспортированному .py запуститься на ПК БЕЗ чего-либо: без websocket-client, без запущенного server.py, без подключённого ESP32. Файл должен импортироваться и пройти до конца, не сломавшись. 

class _Bridge:
    """Заглушка для теста кода на ПК БЕЗ робота."""
    x = 0.0
    y = 0.0
    heading = 0.0

    def set_angle(self, deg): pass
    def move(self, pct):      pass
    def stop(self):           pass
    def set_rgb(self, idx, color, delay=0.0): pass
    def get_distance(self):   return 999.0

Как вплетается в архитектуру

Высокоуровневый класс Robot (forward, arc, face, goto, …) внутри своих методов делает self.set_angle(...), self.move(...) и т.д. — то есть зовёт низкоуровневое API. Python через MRO находит эти методы у _Bridge (родителя в _LiveRobot(_Bridge, Robot)). Поскольку методы _Bridge — pass, ничего физически не происходит. А Python-логика выше (циклы, условия, проверки зон, формулы) — работает нормально.

4.2. Что работает / не работает с заглушкой

Работает ✓

  • Импорт файла, синтаксис — никаких внешних зависимостей
  • Запуск программы до конца (python file.py)
  • robot.load_danger_zones(...), show_danger_zones(), remove_zone(), attention_here() — это просто запись/чтение списков
  • Диагностические print() — зональные предупреждения, WARN: скорость …
  • Контекстная инициализация — расчёт target_heading, dist, cm_per_s
  • Метрики времени — time.sleep() внутри _drive_with_zone_check действительно тикает

Не работает ✗

  • Движение робота — мотор/серва не дёргаются
  • x, y, heading не обновляются — всегда 0.0
  • get_distance() возвращает 999.0 (см. ниже)
  • forward_to_wall() — зависнет навечно: ждёт get_distance() < WALL_STOP_CM, но 999 > 12
  • face(target) — отработает 3 пары forward+back (тик-сны), но heading останется 0. Если потом goto() считал, что повернулся — он ошибётся.
  • goto(50, 60) — сделает все вычисления, проспит положенное время, но x/y не сдвинутся. После 3 попыток «не дошёл» — выходит.
  • Сенсорные ветки (if robot.get_distance() < 50) — всегда False (999 > 50)

Почему get_distance() возвращает 999.0

Robot.forward_to_wall() опрашивает дальномер в цикле, пока расстояние > WALL_STOP_CM. Заглушка должна вернуть что-то. 999 = «бесконечно далеко» — не вызывает мгновенного срабатывания «упёрся в стену». На реальном железе _NetworkBridge.get_distance() шлёт LASER? и парсит ответ.

5. Калибровка под конкретную машинку

Симулятор и реальный 1Т REX едут синхронно только если калибровочные константы соответствуют физическим характеристикам вашей машинки. Настраиваются в config.py или прямо в Настройках UI.

ПараметрДефолтЧто это
SPEED_AT_10080.0 см/с Линейная скорость при 100% мощности мотора. Замерьте: запустите robot.forward(100, speed=100), засеките секундомером.
WHEEL_CIRC_CM28.3 см Длина окружности колеса. Для D90: π × 9 ≈ 28.3 см.
HEADING_DEG_PER_ROT25.0° Сколько градусов курса набегает за один оборот колеса при полном угле руля (45°). Зависит от колёсной базы и радиуса поворота. Замерьте: поставьте руль на 45°, проедьте известную длину дуги, замерьте смену курса по компасу.
TURN_SPEED_REF40 % Опорная скорость, на которой откалиброван HEADING_DEG_PER_ROT. Все геометрические манёвры (arc, K-turn, set_course, …) всегда едут на этой скорости — чтобы дуги были одинаковыми в симе и на железе.
MOVE_SPEED40 % Скорость по умолчанию для прямых forward/back. Можно менять кнопками в UI (MIN/Спокойно/Быстро/MAX).
MIN_SPEED_PCT30 % Минимум — ниже мотор не тянет (рывки, остановки). Все попытки установить меньше клэмпаются автоматически.

6. Поиск и устранение неполадок

ПроблемаЧто проверить
Робот не двигается, в журнале «Bridge connect failed» 1) bridge.py запущен (или Docker-сервис bridge)? 2) В Настройках корректный адрес — ws://bridge:41235 (Docker), ws://127.0.0.1:41235 (нативно) или wss://<name>.trycloudflare.com (туннель)? 3) Индикатор в шапке VEGAREX зелёный (● Онлайн)?
Перезапустите соединение в Настройках (Сохранить).
В логе bridge.py только [DROP] нет канала к ESP32: … ESP32 не подключилась к мосту. Проверь:
  • ESP32 видна в WiFi-сети (роутер/телефон показывает её в списке клиентов)?
  • В /esp-config → 📥 Прочитать — SIP и SPORT совпадают с тем, где сейчас крутится bridge?
  • Windows Firewall не блокирует входящий TCP 8080?
    New-NetFirewallRule -DisplayName "VEGAREX bridge ESP32" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow
  • После SAVE в /esp-config ESP32 действительно перезагружена (reset на плате или передёрнут USB)?
Туннель cloudflared работал, потом VEGAREX «Офлайн» Возможные причины:
  • Окно cloudflared закрылось → URL умер. Запусти заново — URL сменится, обнови его в Настройках.
  • Ноут ушёл в сон — отключи сон на время сессии.
  • Cloudflare разорвал idle-WSS >100 сек. Должно переподключиться автоматически; если нет — Сохранить в Настройках.
Робот двигается, но дальномер всегда показывает 999 Прошивка ESP32 не отвечает на LASER?. Проверь в логе bridge.py: после [→WiFi] LASER? должна прилететь [WiFi→] LASER:42.5. Если ответа нет — проблема в прошивке робота, а не в мосте.
Дуги в симуляторе и на роботе разной формы Калибровка. См. §5. Самое частое — неверный HEADING_DEG_PER_ROT или WHEEL_CIRC_CM.
Робот промахивается по точкам в goto Накапливается дрейф dead-reckoning. Причины: проскальзывание шин, неверная SPEED_AT_100, батарея просела (мотор недодаёт). Калибровка + MPU-гироскоп для курса.
Голос «Вега вперёд 50» не распознаётся Web Speech API работает только в Chrome/Edge. Микрофон должен быть разрешён (значок в адресной строке). На удалённом хостинге нужен HTTPS, на localhost — без сертификатов.
Робот въезжает в препятствие, программа не реагирует 1) Зоны загружены в robot.load_danger_zones(...)? 2) Координаты препятствий совпадают с реальными? 3) В Настройках «Препятствия → ⛔ Опасные зоны» включено? Робот не «видит» препятствия в физическом мире — только через свой dead-reckoning + загруженный список зон.
Экспортированный .py падает: ModuleNotFoundError: websocket pip install websocket-client на той машине, где запускаешь скачанный файл. Важно: именно websocket-client, не websocket.
